Popover positioning has no collision detection, and an ancestor with overflow: hidden will clip it. It's absolute offsets against a relative wrapper — marked ponytail: in the source. That's exactly the trade P4_Plan.md flagged; if flipping near a viewport edge starts mattering, that's when a positioning engine earns its place. Dialog and Drawer don't have this problem — the top layer is the browser's.

Two real bugs my own tests caught: the menu's active index never synced with actual focus, so arrowing after a Tab or click started from the wrong item (fixed with onFocus); and Biome correctly rejected my first attempt at putting the key handler on a wrapper <div> — the handler now lives on the buttons, which are the real focus targets.

Nothing here is in the playground showcase yet, and none of it has been seen in a browser. The Popover placements and the Sidebar modes in particular want a real look — jsdom can't tell you whether a panel is clipped or a sticky sidebar actually sticks. Want me to add showcase sections?

===============================================================
GOING MULTIPLATFORM — Vue, React Native, Angular
===============================================================
The good news: the biggest asset already exists and is framework-agnostic —
styles.css's design tokens are plain CSS custom properties, not React. Any
framework that can load Tailwind + that stylesheet inherits the same
palette, spacing, and dark-mode behavior for free. cva's output is also just
a string of class names — it doesn't care what rendered the DOM node.

What does NOT carry over, by platform:

Vue — moderate lift.
  - Every component becomes a Vue SFC (or a .tsx render function using Vue's
    JSX). Hooks (useState/useRef/useEffect) become Composition API
    (ref/computed/watchEffect). Custom hooks like useDismiss port to
    composables almost 1:1 — same lifecycle shape.
  - Native <dialog>, matchMedia, and the CSS keyframes/@starting-style
    approach used in Dialog/Drawer/RunBanner all work unchanged — they're
    DOM/CSS, not React.
  - Icon set: swap @tabler/icons-react for @tabler/icons-vue (same names,
    same tree-shaking story).
  - Slot-based composition (Card's Header/Body/Footer, Tabs' <Tab> children)
    maps onto Vue slots/named slots reasonably closely.

Angular — moderate-to-heavy lift.
  - Components become Angular standalone components with templates;
    render-prop patterns (Tabs' renderTrigger, Toaster's render) don't exist
    natively — Angular's equivalent is ng-template + ContentChild/structural
    directives, which reads very differently and is more verbose to write
    and to consume.
  - Tokens, cva output, and the native-<dialog> primitives still carry over
    unchanged (same reasoning as Vue).
  - Reactive state maps to Signals; the controlled/uncontrolled dual-prop
    pattern (value/defaultValue, checked/defaultChecked — used throughout the
    form atoms) needs a deliberate Angular idiom decision up front, since
    Angular has no single established convention for it the way React does.

React Native — this is not a port, it's a second design system that happens
to share a name and a palette.
  - No DOM. No Tailwind CSS. No <dialog>, no CSS keyframes, no
    @starting-style, no backdrop-filter, no CSS ::backdrop. Everything in
    Dialog/Drawer/Popover/DropdownMenu/RunBanner's animation layer is
    web-only and has to be rebuilt on React Native primitives (Modal,
    Animated or Reanimated, PanResponder/Gesture Handler for dismissal).
  - No CSS classes at all — cva's string output is useless here. Tokens
    would need to ship as a plain JS/TS object (colors, spacing, radii) and
    every component styled via StyleSheet.create or a RN-specific styling
    library (NativeWind is the closest thing to keeping the utility-class
    authoring style, but it's a different runtime).
  - The form atoms lean on native inputs (appearance-none checkbox/radio,
    native <select>, <textarea> scrollHeight measurement) — none of those
    exist on RN. Checkbox/Radio/Switch/Select all become bespoke Pressables.
  - Maps' Leaflet/DOM basis doesn't exist on RN at all — would need
    react-native-maps, a different API entirely, not a port.
  - Icon set: @tabler/icons-react-native exists with the same names, so the
    registry pattern (icon-registry.ts) itself ports, just re-pointed at a
    different package.
  - Positioning (Popover's absolute-offset placement, FlyContainer's vh/vw
    math) has no DOM measurement API — RN uses onLayout + measure() instead
    of getBoundingClientRect, and there's no CSS position:fixed, so
    everything floating needs its own Portal + manual layout math.

Recommended structure if this is genuinely on the roadmap: split into a
framework-agnostic "core" package (design tokens as a plain object + CSS
export, the icon-name registry, pure logic with no DOM/React dependency —
getPageRange, debounce, the marker-icon resolution, Avatar's initials
derivation, contrast-checked color values) and separate per-framework
packages (@rakit-ui/react — this repo, @rakit-ui/vue, @rakit-ui/angular,
@rakit-ui/native) that each own their own rendering, animation, and
positioning story on top of that shared core. Don't attempt one codebase
that renders to all four — the primitives (dialog focus trap, positioning,
animation, form controls) are different enough per platform that a shared
abstraction over all of them ends up leakier than four separate, consistent
implementations.

Ordering, if picked up: Vue first (cheapest — same DOM/CSS, "just" a
different component model), then Angular (same primitives, more verbose
API surface to design), then React Native last (genuinely a second
product, budget accordingly — it's closer to a rewrite than a port).
